Why latency stays nearly constant up to concurrency 32

At concurrency 1→32, p50 stays near 42ms (RTT + 1.9ms server time), while throughput increases linearly by 28x. This range fills the connection and overlaps RTT waiting time; the server is not yet saturated. At concurrency 64 and above, p50 starts rising (50 → 100ms), indicating server-side queuing. In other words, cross-region access adds fixed latency per operation without limiting aggregate throughput.

2. Effect of batch size

Keep concurrency at 8 and vary only the insertMany batch size. This explains why production code uses insertL0Batch instead of individual upserts.

batch=1000 maximizes throughput at a high tail-latency cost

Increasing batch size from 100 to 1000 improves throughput by only 34% (14.7k → 19.8k), while batch p99 rises from 148ms to 889ms. For online writes, batch=100 is a better tradeoff; batch=1000 is suited to offline bulk loading.

6. Conclusions and caveats

Capacity demonstrated

100 million messages were written with 0 errors, the $search index is available, and concurrent business queries reach hundreds of QPS. Dataset size itself is not the issue.

Maximum throughput per operation

Single-document inserts (batch=1) into an empty collection reach 2,184 docs/s at concurrency 256, 92x the serial 23.6/s. Serial throughput is low because each operation waits for a 39ms round trip while the server takes only 1.9ms. With sufficient client concurrency, cross-region access has little effect on aggregate throughput.

The two actual limits

Writes: index maintenance lowers throughput as the collection grows (24k/s → 930/s). For historical data loading, consider creating the collection first, then building the $search index to avoid maintaining an inverted index during writes.
Reads: mongot BM25 queries peak at 215 QPS, the lowest read-path ceiling. Plan capacity around this limit.
